# 设备密钥收起/恢复的队列死锁：复现、修复和验证

日期：2026-10-18。处理 Hermes r3 第 11 轮的等待环发现。基于当前含未提交修改的主工作区；本轮前保存了 442 个来源文件的哈希与 Git 状态。保留 r1/r2/r3 的独有源码和报告，不套用旧候选补丁。

## 原因与范围

旧调用链：`discardStoredPendingDeviceKey` / `restoreRecoverableDeviceKey` → 设备队列 → 秘密写入队列 → `listWallets` → 历史索引去重 → `removeSecret` → 同一个秘密写入队列。外层等待去重，内层删除又排在外层之后，互相等待。

触发条件是索引至少有两条同链、同账户、同公钥但不同 ID 的历史钱包记录，并且在普通列表读取完成去重前执行收起或恢复。影响为当前操作及后续秘密写入、改密挂起，通常需重启应用解除；本轮没有证明密钥泄露、链上权限改变或资金损失。上轮保留密钥机制的回归缺少此条件，本轮补齐该覆盖。

## 修复

`src/crypto/vault.ts` 提取私有的纯读取函数 `readStoredWalletIndex`，负责已有的存储重试、读取/JSON 错误处理，并拒绝非数组索引。收起/恢复只用它核对目标 ID 是否已经导入，不在持有秘密写入队列时触发清理。

公开的 `listWallets` 仍在纯读取后运行原有去重、权限合并及废弃秘密/生物识别槽位清理。设备事务和秘密写入队列、先保存恢复记录再清 pending 的顺序、密文保留、恢复不覆盖另一活动密钥的保护均保留。本轮没有调整跨模块锁顺序，也没有解决全部钱包索引并发风险。

## 回归与验证

新增 `src/crypto/__tests__/vaultQueueReentrancy.test.ts`，每个测试独立加载 vault 与存储适配器，避免旧实现的故意死锁污染其他用例。SecureStore 使用内存 Map，原生 PBKDF2 替换为 Node crypto 的同一算法；使用实际密码派生和 AES-GCM 密文保存合成秘密，没有访问真实钱包或凭据。

- 收起/恢复各一项：以两条重复历史索引触发操作，观察到索引读取后再排入一个秘密写入。要求操作和后续写入均完成；检查操作没有改动历史索引或密文；再验证主密码轮换、两个重复 ID 和设备秘密均可解密，以及正常 `listWallets` 仍能去重合并权限并删除重复槽位。
- 收起/恢复各一项：目标 ID 已在重复索引中时必须拒绝，保留所有记录与密文，且后续秘密写入可完成。
- 收起/恢复各一项：非数组索引必须以读取错误拒绝，存储不变且队列继续工作。

最终运行 `validation-2`：旧源码收起与恢复两条对照均因队列未完成而失败（2 项），修复版 4 个定向套件 109 项测试通过；全量 Jest 102 个套件、1024 项通过；工具链测试 40 项通过、5 项按平台跳过、0 失败。TypeScript、依赖策略/补丁和来源签名通过（invalid/missing 均为空）。Expo 按 SDK 自带映射做离线兼容检查通过，日志提示离线检查可靠性有限，不能称为在线全量验收。第一轮运行 `validation-1` 的全部 1024 项测试也通过，但新增测试辅助函数的联合返回类型声明使 TypeScript 失败；仅修正该声明，未改业务实现，第二轮完整重跑通过。两轮日志均保留。旧源码来自本轮开始前的 `before-source`，对照前与 `before-manifest.json` 核对 SHA-256。对照与修复版使用同一批依赖，对照后恢复最终源码；不是使用上轮 1018 项测试代替本轮结果。

沿用项目隔离验证：固定镜像摘要、非 root、只读根、无宿主凭据、禁用依赖安装脚本；安装阶段执行依赖策略与 `npm audit signatures`，项目代码执行断网。NAS 访问 npm/Sigstore 使用仅允许两个公开目标的临时 HTTPS CONNECT 通道，保留端到端 TLS 和来源签名检查。没有降低隔离或修改依赖策略哈希，没有绕过 Hermes 自身运行时的拒绝。

证据目录：`exports/vault-queue-security-2026-10-18/`。未构建、签名或发布安装包；未真机验证原生 Keystore。本机内存适配器不能代表所有原生存储故障。
