# 完整安装包更新

钱包只通过完整安装包更新。`app.json` 显式设置 `updates.enabled: false`，项目没有接入 `expo-updates`、EAS Update 或远程 JavaScript 包。

## 客户端行为

- 每次冷启动进入前台时检查一次，不需要登录或打开“我的”。
- 从后台回到前台时，如果距上次检查超过五分钟，再检查一次；强制更新弹窗尚在时，每次回到前台重新检查，以便后台撤回或调整策略。
- 自动检查失败不弹错误提示，不阻断正常启动；“我的 → 检查更新”仍会明确显示检查结果和错误。
- 自动检查与手动检查合并并发请求，全应用只有一份更新弹窗。
- 普通更新显示版本、标题和更新说明，可选择“稍后”。同一次启动不再自动提示同一个普通版本；手动检查、新版本或改为强制更新不受该限制。下次冷启动会重新检查和提示。
- 普通自动提示会等待当前钱包确认弹窗关闭，避免遮住正在处理的操作。
- 强制更新没有关闭或“稍后”入口，遮罩、Android 返回键和后来打开的普通弹层不能绕过提示。它限制客户端界面的继续使用，不代替操作系统确认安装。
- 后台停用版本后，下一次成功检查会移除对应提示；网络故障不会擅自撤销已经收到的强制更新策略。

Android 用户点击“立即更新”后下载 APK，展示进度，下载完成调用系统安装器。系统可能要求授权“允许安装未知应用”；返回后点击“安装”可再次打开安装器，无需重新下载。新包必须与已安装钱包保持相同包名和签名。

iOS 用户点击“立即更新”后打开后台配置的 HTTPS 安装或商店页面，按系统流程更新。正式版填写 App Store 页面，TestFlight 测试版填写 TestFlight 链接，EAS Ad Hoc 测试版填写可安装的 EAS 页面。不要填写裸 IPA 文件地址；Ad Hoc 安装设备仍须包含在新包的描述文件中。

## 后台发布

进入 `https://eos3.app/admin/` → **版本更新**，分别选择 iOS 或 Android：

1. 先准备并验证可安装的新包，再填写下载或安装页面地址。
2. 填写版本名（如 `1.0.5`）和递增的整数版本码。Android 对应 `versionCode`，iOS 对应安装包内的 `CFBundleVersion`；不要用版本名称或 EAS 构建 UUID 代替。当前 iOS 测试包为 `1.0.4 (26)`，后续包使用更高构建号。
3. 填写标题和更新说明。客户端按后台文本原样展示，不执行 HTML 或脚本。
4. “启用”决定是否发布该条记录；“强制更新”决定低于该发布版本的客户端是否必须升级。
5. 如只要求特别旧的客户端升级，关闭“强制更新”，设置“最低支持版本码”；低于该码的客户端仍收到强制更新提示，其余旧版收到普通提示。
6. 保存发布。每个平台选择已启用记录中版本码最高的一条。草稿或停用记录不会提示更新；停用最高版本时，更低的已启用记录仍可能被选中。

检查接口：

```text
GET /api/app-update/check?platform=ios&versionCode=26
GET /api/app-update/check?platform=android&versionCode=3
```

管理员读取和保存版本目录使用现有 Bearer 管理员会话：

```text
GET /api/admin/app-update/releases
PUT /api/admin/app-update/releases
```

服务端按平台及版本码判断更新，计算 `forceUpdate || 当前版本码 < minVersionCode`。客户端再次核对版本码、平台、字段类型和 HTTPS 地址，拒绝同版、降级、错误平台及无效配置。请求禁用 HTTP 缓存，避免复用过期的更新策略。

现有后台和 Go API 已支持上述字段，不需要修改数据库或新增接口。本次接通的是原生钱包的启动检查和全局弹窗，未在生产后台创建任何发布记录。用户需先安装包含该功能的新完整安装包；旧安装包无法通过后台配置补上尚未包含的启动检查代码。
