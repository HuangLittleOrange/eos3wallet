# 钱包安全续查：开户身份与 DApp 请求撤销

日期：2026-10-18。在此前修复后的当前工作区上继续检查，确认两处问题，随后按用户要求完成修复及回归，状态均为**已修复并回归通过**。未生成或发布新安装包。下面 C1、C2 的攻击步骤和原始证据保留为修复前记录。

## 修复实现与回归结果

**C1 已修复。** 新增 `verifyCreatedAccount`，复用此前账户导入核验的权限规范化和可信节点传输：至少两个不同的内置 HTTPS RPC 主机返回一致的账户权限，校验链 ID 和账户名，再在本机比较新公钥及权重。当前选择的 RPC 只能提供查询候选，不能单独决定开户成功。

付费开户在显示“账户已创建”之前核验一次，在验证主密码之后、读取待保存私钥和写入正式钱包之前再次无缓存核验。新密钥必须直接满足 Active 或 Owner 中至少一个权限的阈值；保存的权限列表也只包含该密钥直接满足阈值的权限，默认优先 Active、其次 Owner，再列自定义权限。正常 Owner/Active 同钥、Active 单钥及 Owner 单钥均可保存，普通导入的合法部分多签成员能力保持不变。

所有核验请求仅发送账户名，不发送私钥、密码或新公钥。单个恶意来源不能独自取得多数；这仍是可信节点方案，不是轻客户端证明，也不能证明密钥独占控制或防止两个信任来源串通。

账户不存在时继续保留原有激活轮询；核验失败显示错误并保留订单及待保存密钥供重试，不显示开户成功、不切换收款账户。保存失败或取消发生在加密完成、钱包索引写入之前时，清理本次新建的孤立密钥槽位，保留原恢复材料；索引已经写入的有效钱包不会被取消流程删除。重复提交只执行一次保存。链、节点或订单变化、退出页面和正常进入后台会废弃旧核验。开户保存与订单绑定，不依赖付款钱包是否改变，因此第一次保存后钱包列表自动选中新账户不会误取消正常完成。

名字可用性检查不再把所有错误当作可用：只接受 `get_account` 的明确不存在错误；断网、代理或其他错误显示重试提示。修改名字后必须检查新名字，不能沿用旧名字的检查结果。另修正付款成功后立即激活时重复用旧订单覆盖交易编号和区块浏览器链接的问题，支付金额、合约和 memo 保持原有生成方式。

**C2 已修复。** `disconnect()` 删除连接授权，同时递增请求代次并清空旧请求实例。页面先返回 `forgetIdentity` 成功回执，再撤销旧请求，清理待连接状态、签名确认状态及扫码请求。重新连接只能授权新的请求，旧请求即使复用相同 ID 也不会恢复。

异步公开查询、原生连接弹窗按钮及 TokenPocket 扩展回应也绑定原请求实例，避免旧回调误回应重新连接后的同 ID 请求。交易解码和签名前后已有的实例检查继续生效，正常文本签名、序列化交易签名和重新连接保留。

## C1：付费开户入口仍可保存不属于新密钥的账户

**优先级 P1，条件成立时影响后续收款。** 上一轮修复了私钥、助记词和设备密钥导入，但漏掉了 `CreateAccountPayScreen` 开户后的保存入口。这是相同身份信任问题在另一入口的残留，不能理解为上一轮导入修复完全没有生效。

位置：`src/screens/CreateAccountPayScreen.tsx:176`、`:298`、`:374`。

账户可用性检查把 `getAccount` 的所有异常都当作“名字可用”。激活轮询随后只要能查询到账户，就进入成功页；即使本地生成的公钥不在返回的任何权限中，`mine=[]` 也不会阻止保存。最终保存只验证主密码和本地待保存密钥，没有调用独立账户权限核验，仍然写入该账户并切换当前收款身份。

**具体攻击条件：** 攻击者控制用户所选 RPC，并且用户填写的账户名实际已由攻击者控制，或攻击者能在开户竞态中先取得这个名字。RPC 先把已有账户伪装成不存在，稍后返回该账户，钱包就可能误报“开户成功”。攻击者不能通过这条路径随意把用户输入的名字改成另一个名字；随机选择且攻击者没有取得的账户名不满足这一资金截获条件。

**离线复现：** 执行真实开户页面的“输入名字 → 检查可用 → 生成订单 → 外部付款入口的激活检查 → 输入主密码保存”，没有预先注入已保存钱包。第一次模拟 RPC 查询报错，第二次返回账户及另一个测试公钥的 Owner/Active 权限。真实页面仍保存本地新公钥与该账户的组合，清除待保存密钥槽位、报告成功并切换账户。再执行真实收款页面，其二维码指向攻击者控制的测试账户 `attacker`。

该证据没有执行真实付款、开户合约或链上抢注。界面报成功不证明开户付款已成功；风险在于随后把这个二维码当作本人地址充值，资产会进入账户实际控制者手中。私钥没有因此泄露，原有钱包余额也不会在保存时自动转出。

**修复建议：** 在成功展示和最终保存边界核验账户名、所选链及新公钥的实际权限；最终保存必须独立读取权限，不能仅凭当前 RPC 的候选结果或非空账户响应。复用已有可信节点核验，并根据开户应获得的权限检查阈值。核验失败保留订单和待保存密钥供恢复，不保存或切换收款身份；同时绑定异步流程的订单和钱包上下文。

## C2：DApp 断开再连接可恢复原本应失效的签名请求

**优先级 P2，撤销边界失效。** 位置：`src/dapp/accessGuard.ts:74`；`src/screens/DappBrowserScreen.tsx:282`、`:427`。

`disconnect()` 只删除连接授权，没有递增请求代次，也没有清除旧请求。页面处理 `forgetIdentity` 时虽然关闭确认界面，却未使已经运行的异步签名闭包失效。该闭包的 `isCurrent()` 要求当前已连接且旧请求仍在表中；在等待认证或资源查询时，若同一个页面重新连接，两项条件会再次同时成立。

**已完成两种离线复现：**

1. 用户确认一条文本签名，请求等待模拟解锁完成；页面断开，钱包关闭原确认界面；用户同意重新连接后，旧请求仍取得有效文本签名。
2. 用户确认一笔序列化交易，解锁已完成，真实 `preflightDappResources` 等待模拟 RPC 正文；页面断开并经用户同意重新连接；RPC 查询结束后，旧交易继续取得有效签名，不再要求确认该笔交易。

两种情况均执行真实 `DappBrowserScreen`、`DappAccessGuard` 和 `signDigest`，并用测试公钥验证返回签名。交易变体还执行真实交易解码、可见内容检查和资源预检查；ABI 读取被替换为固定本地测试 ABI，未模拟恶意 ABI。原生界面、存储和解锁由内存适配器替代。交易使用合成链 ID，没有广播。

**影响边界：** 需要用户此前已经确认原请求，并在异步操作结束前同意同源、同钱包上下文的重新连接；攻击者不能据此修改已经确认的收款人、金额或消息，也不能直接要求签署任意新内容。这里确认的是旧授权在断开后恢复的问题。没有重新连接时，当前连接检查仍会阻止交付；使用已有 `cancelPending()` 后，旧闭包即使遇到重新连接也不会恢复，这两个反向断言均已通过。

**修复建议：** 断开时永久废弃当时的请求实例和仍待用户操作的连接请求；重新连接只能授权新请求。保留 `forgetIdentity` 自身的成功回应，避免清空请求表后丢失断开回执。针对解锁等待、资源预检查、解码等待、同 ID 重用和重新连接补充回归。
