# 钱包列表、设备重复导入与设备密钥发布：复现、修复及验证

日期：2026-10-18。处理 Hermes r5 第 25、26 轮发现的三个独立入口。任务开始记录当前含未提交修改的 446 项公开来源文件 SHA-256、Git 状态和 6 个待修改文件原件。保留所有此前修复与 r1–r5 审计源码、报告。开发前按 AGENTS.md 读取 [Expo SDK 57 文档](https://docs.expo.dev/versions/v57.0.0/)。

## 三个问题与最终行为

1. **启动读取钱包列表误删唯一好密文。** 旧 `listWallets → dedupeStoredWallets` 按最早创建时间选旧 ID，没有确认旧槽存在、可解密或公钥正确，就删其他槽，之后才尝试写索引。修复后列表只是非破坏性视图，不写索引、不删密文或生物识别凭据。重复项只有一份非空本地密文时优先展示该 ID；多份非空密文分别按 ID 保留可选，并合并权限展示。非空只用于选择提示，绝不当作私钥正确性证明。原始索引完整保留；明确输入当前密码的 `addWallet` 仍走上一轮验证、修复缺槽及提交后清理事务。钱包列表与 `switchWallet(id)` 已支持选择具体 ID，签名器仍核对解密后的公钥。代价是异常历史记录可能显示多个同账户副本，不能为了去重外观无认证销毁恢复材料。
2. **设备重复导入误删好 pending 密文。** 旧 `importPendingDeviceKey → importStoredPendingDeviceKey` 的正向链权限 quorum 只证明公钥在链上有权限，不证明旧本地密文正确；旧槽非空便复用旧 ID，删 pending 好密文。修复后将当前设备钱包以自己的 pending ID 写到索引前部，合并已知权限，保留全部旧记录和旧密文；确认索引提交后才清 pending 元数据，不删除该密文。设备与秘密事务使用统一的设备队列→秘密队列顺序；索引失败或读回不确定时保留 pending 和所有密文；清 pending 提交后报错可读回确认，明确未清除则可重试同一 ID。权威索引修改（普通添加、设备导入、明确删除）共用秘密队列及原始完整索引，避免把过滤后的显示视图写回存储。
3. **设备首次发布提交后报错，失败清理又删密文。** 旧 `createPendingDeviceKey` 在 pending 元数据保存抛错后无条件删除新槽。修复后先读回判定匹配的记录是否已发布：已确认提交继续返回可用 pending；明确未发布且没有钱包、pending 或恢复引用时，仅清本次未发布的新槽；结果无法读取时保留密文及秘密 ID 注册表，并尽可能保存可发现的设备恢复记录。结算在设备与秘密队列中完成，覆盖已被消费进钱包、已归档、同 ID 其他 pending 等情况，避免并发消费后误删。页面生成失败后重新读取实际 pending/恢复状态。

没有放宽链身份、正向权限 quorum、取消检查、签名公钥核验或系统认证；没有修改依赖、锁文件、执行策略、模型或服务。既有列表与队列回归中的“无密码列表应清重复槽”断言随契约改为“不写、不删、保留所有恢复材料”；明确未提交的新设备槽清理通过新增真实 vault 集成测试继续验证，没有删除该安全要求。

## 复现与验证证据

新增 `src/crypto/__tests__/vaultSurvivorSafety.test.ts`，28 项回归。运行真实 vault、设备生成/导入调用链、K1 公钥派生、PBKDF2-HMAC-SHA256 与 AES-GCM；原生 PBKDF2 用 Node crypto 实现替身，SecureStore 为可注入提交/读回故障的内存 Map。所有密钥均随机生成、无资金，网络为模拟响应。设备重复导入走实际选择节点核验及内置正向权限 quorum；另验证“只有自选节点声称授权”不能提交。

旧源码按任务前哈希验证后，使用同批来源签名检查通过的依赖运行 7 项对照，全部按行为预期失败：列表缺槽/已轮换代次 2 项、设备重复槽损坏/错钥/缺失/正常 4 项、设备发布提交后报错 1 项。列表 2 项、设备损坏/错钥 2 项及发布 1 项直接在实际解密时得到 keyNotFound；设备正常旧槽对照说明旧实现会删当前副本，但正常旧副本仍可用；设备缺槽对照是旧实现拒绝导入，不称为额外密钥丢失。原始失败日志保留，不能把退出码 1 单独作为复现依据。

修复后的覆盖包括列表重复加载不写不删、多个副本和权限、跨链/显式删除不丢隐藏索引、认证重新导入、设备正常导入、代次/密码轮换、索引未提交/提交后报错/读回未知、pending 清除失败及重试、确定未发布清理、未知发布可恢复、恢复元数据也不可写时保留密文、钱包/恢复/pending 引用保护和并发生成只发布一把钥。此前队列死锁及重新导入测试全部保留。另增 2 项页面回归，确认生成错误后仍能显示已保存 pending 或恢复入口；生物识别取消测试改为在真实 requireAuthentication 槽注入错误，不依赖读取次数，并继续断言取消不迁移或破坏凭据。

最终有效运行以 `exports/survivor-security-2026-10-18/validation-2/` 为准：7 项旧源码行为对照按预期失败；9 个定向套件、194 项通过。全量 Jest 104 个套件、1076 项通过；工具链测试 40 项通过、5 项按平台条件跳过、0 失败。TypeScript、依赖策略/补丁和注册表来源签名通过（invalid/missing 为空）；Expo 使用 SDK 自带离线映射检查通过，日志明确标注离线模式可靠性限制，不称为在线完整兼容验收。本报告不把此前 1046 项测试当作本补丁通过证据。第一轮定向为 191 项通过、1 项旧生物识别故障注入位置错误导致失败；已改为按认证槽注入而非读取序号，并避免无重复项时多读代次标记，第二轮包含该安全断言及新增页面回归全部通过。第一轮原始日志保留，不替代最终验证。

## 范围与限制

沿用项目固定镜像摘要、非 root、只读根、禁用安装脚本的无凭据隔离 worker；项目代码执行断网。安装与来源验证只通过临时、限定 npm/Sigstore 两个公开目标且保持端到端 TLS 的 CONNECT 通道。没有绕过 Hermes 自身仍受约束的执行拒绝。

提交后报错、读回不可用为存储适配器故障注入，不能推断原生 Keystore 实际发生频率。尚未进行真机存储故障验收、构建、签名或发布。存储持续不可读/不可写时无法保证恢复元数据可发现，但不主动删除已登记密文；历史已经丢失且没有备份的私钥无法由补丁重建。保留的异常旧槽会令整库密码轮换继续保守拒绝，直到用户明确处理不一致副本；不能静默跳过或覆盖它们。
